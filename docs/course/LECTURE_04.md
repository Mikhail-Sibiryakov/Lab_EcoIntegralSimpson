## 1. Повторное использование в ACOM

**Слайды 2–4.** ACOM поддерживает наследование интерфейсов, но не наследование
реализации. Повторное использование реализации строится через включение
(containment) и агрегирование (aggregation). Мотивация — уменьшение зависимости
одного компонента от внутреннего устройства другого.

Смена реализации компонента не должна заставлять клиента обращаться к его
внутренним структурам. Совместимость обеспечивается опубликованным интерфейсом.

## 2. Включение

**Слайды 5–6, 10–15.** Внешний объект выступает клиентом внутреннего:

- получает интерфейс внутреннего объекта;
- хранит указатель на этот интерфейс;
- вызывает через него методы;
- при необходимости реализует такой же интерфейс снаружи и перенаправляет вызовы,
  добавляя собственную обработку до или после вызова.

В примерах при инициализации внутренний компонент создаётся через
IEcoInterfaceBus1::QueryComponent. Параметр внешнего IEcoUnknown при обычном
включении равен нулю. Из методов внешнего интерфейса вызываются методы внутреннего.

Это не требует доступа к HeaderFiles или SourceFiles внутреннего компонента
из кода внешнего: взаимодействие идёт через опубликованный интерфейс.

## 3. Агрегирование

**Слайды 7–8, 16–21.** Внешний объект предоставляет клиенту интерфейс внутреннего
объекта непосредственно. Внутренний компонент должен специально поддерживать
такое использование.

Основные части:

- управляющий IEcoUnknown внешнего объекта;
- неделегирующий IEcoUnknown внутреннего объекта;
- делегирующее поведение QueryInterface, AddRef и Release публичных интерфейсов
  внутреннего объекта.

При агрегировании внутренний объект направляет операции своего публичного
IEcoUnknown к управляющему IEcoUnknown внешнего объекта. Для самостоятельного
использования делегирование направляется к собственному неделегирующему IEcoUnknown.

Внешний объект хранит неделегирующий IEcoUnknown внутреннего и использует его
для получения внутренних интерфейсов и управления внутренним объектом.
В примере запроса внутреннего компонента передаются:

- CID внутреннего компонента;
- указатель внешнего IEcoUnknown;
- IID_IEcoUnknown;
- выход для указателя внутреннего IEcoUnknown.

Внешний QueryInterface перенаправляет запрос поддерживаемого внутренним объектом
интерфейса через сохранённый внутренний IEcoUnknown. Публичный QueryInterface
внутреннего объекта делегирует запрос управляющему внешнему IEcoUnknown.

**Проверяемое следствие для реализации:** переходы между публичными интерфейсами
должны работать в обе стороны; управление ссылками должно оставаться согласованным.
Требование продемонстрировать такие переходы во второй лабораторной содержится
непосредственно в Задание_2.pdf, страницы 2–3.

## 4. Несколько интерфейсов и повторное использование

**Слайды 9, 22.** Включение удобно, когда внешний компонент контролирует
предоставляемый интерфейс и обработку вызова. Агрегирование позволяет повторно
использовать уже подходящую реализацию интерфейса без дополнительной реализации
каждого его предметного метода снаружи.

Интерфейсы IEcoCalculatorX и IEcoCalculatorY на слайде 22 иллюстрируют развитие
компонента: клиент, знающий только X, продолжает работать, даже если компонент
поддерживает дополнительный Y.

## 5. QueryInterface и фабрики

**Слайды 23–29.** QueryInterface выбирает поддерживаемый интерфейс по IID.
Это получение другого интерфейса существующего объекта.
Сравнение с простой фабрикой на слайде 28 — объяснение шаблона, а не требование
создавать новый объект на каждый QueryInterface.

**Слайды 30–35.** Фабрика компонента реализует IEcoComponentFactory.
Alloc и Init отвечают за создание и инициализацию объекта.
Если объект использует другие компоненты, их получение входит в его инициализацию.
В приведённом устройстве фабрики создание и инициализация передаются
вспомогательным функциям конкретного класса.

**Слайды 36–39.** Интерфейсная шина рассматривается как фабрика фабрик.
Клиент получает компонент через IEcoInterfaceBus1::QueryComponent с CID компонента
и IID нужного интерфейса. На слайде 39 показана связь запроса клиента с работой
фабрики и возвратом интерфейса.

QueryComponent и QueryInterface выполняют разные роли:
первый используется для получения компонента через шину,
второй — для перехода между интерфейсами уже полученного объекта.

## 6. Как использовать примеры лекции

Фрагменты C на слайдах неполные и не являются готовыми исходниками.
Сигнатуры, типы и соглашения вызова проверяются по публичным SharedFiles SDK
и калькуляторов из Eco.Education.

В частности:

- на слайде 28 написано QueryIntrface — в коде требуется QueryInterface;
- на слайде 33 упомянут IEcoBase.h; публичные интерфейсы нашей установки и примеров
  подключают IEcoBase1.h;
- пример создания на слайде 20 показывает ветку с внешним объектом; полноценное
  поведение самостоятельного объекта нужно сверять с Lesson03/Eco.CalculatorB;
- смещения между интерфейсами из учебных фрагментов нельзя переносить без проверки
  фактической структуры объекта и целевой архитектуры;
- поддержка внешнего агрегирования и использование других компонентов внутри
  являются отдельными возможностями.
