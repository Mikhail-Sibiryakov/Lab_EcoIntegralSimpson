# Лекции 1–3: общие положения ACOM

Переиспользованы положения из ранее подготовленной выжимки лекций первой работы.
Применения, относящиеся только к заданию 35, не перенесены.
Слайды и исходные PDF указаны в каждом разделе; источник находится в общем Materials.
Применение к лабораторной 2 определяется TASK.md и DESIGN.md в docs/lab2.

### L1-A. Eco и среда выполнения

**Положение лекции:** Eco позволяет создавать решения для bare metal с микроядром
и для существующих ОС с унификационным ядром. В архитектуре показаны интерфейсная
шина, загрузчик, менеджер памяти и другие сервисы.
Источник: [L1, слайды 16–18](<../../../../Materials/Presentations/Проектирование - Лекция 01.pdf#page=16>).

### L1-B. Интерфейсы обеспечивают расширение функциональности

**Положение лекции:** пример калькулятора показывает совместимость старого
клиента со старым интерфейсом и добавление функций через другой интерфейс.
Источник: [L1, слайд 19](<../../../../Materials/Presentations/Проектирование - Лекция 01.pdf#page=19>).

### L1-C. Цель практической работы

**Положение лекции:** программа курса включает компоненты и интерфейсы ACOM,
IEcoUnknown, UGUID, фабрики, обратные вызовы и сервисы ОС. Практика предполагает
разработку компонентов и решений, которые используют эти компоненты;
оценка по ACOM связана с разработкой компонента выбранного задания.
Источник: [L1, слайды 31–33](<../../../../Materials/Presentations/Проектирование - Лекция 01.pdf#page=31>).

### L1-D. Откуда берётся правило C89

**Положение лекции:** на слайде 35 C89 указан в требованиях к курсовым и дипломным
работам; слайд 38 перечисляет стандарты C и MISRA.
Источник: [L1, слайды 35 и 38](<../../../../Materials/Presentations/Проектирование - Лекция 01.pdf#page=35>).

### L2-A. Назначение компонентного подхода

**Положение лекции:** приложение составляется из компонентов; компонент можно
заменять, адаптируя решение и повторно используя готовую функциональность.
ACOM похожа по концепции на COM/XPCOM, но их реализации не совместимы.
Источник: [L2, слайды 2–5 и 9](<../../../../Materials/Presentations/Проектирование - Лекция 02.pdf#page=2>).

### L2-B. Компонент, интерфейс и экземпляр — разные сущности

**Положение лекции:** модель компонента включает уникальное имя, набор интерфейсов,
фабрику, реализации и системные сервисы. Спецификация интерфейса включает
типы, константы и сигнатуры методов. Клиент взаимодействует с компонентом
через интерфейс.
Источник: [L2, слайды 16–19](<../../../../Materials/Presentations/Проектирование - Лекция 02.pdf#page=16>).

### L2-C. Идентификаторы и варианты сборки

**Положение лекции:** ACOM использует UGUID для идентификаторов интерфейсов,
компонентов и поколений. Компоненты могут поставляться статическими и динамическими
библиотеками; ACOM не ограничена динамическими библиотеками.
Источник: [L2, слайды 10–12](<../../../../Materials/Presentations/Проектирование - Лекция 02.pdf#page=10>).

### L2-E. Опубликованный интерфейс нельзя изменять

**Положение лекции:** опубликованный интерфейс всегда сохраняется; новая
функциональность добавляется новым интерфейсом. Пример калькулятора показывает
совместимость клиентов старой и новой версий.
Источник: [L2, слайды 27–35](<../../../../Materials/Presentations/Проектирование - Лекция 02.pdf#page=27>).

### L2-F. Представление интерфейса в C

**Положение лекции:** интерфейс представлен структурой с указателем на VTbl;
VTbl содержит указатели на функции. В C первым аргументом метода передаётся
указатель `me`. Описание интерфейса задаёт формат, но само не создаёт экземпляр.
Экземпляр содержит указатели на таблицы и собственные данные.
Источник: [L2, слайды 28–29 и 37–40](<../../../../Materials/Presentations/Проектирование - Лекция 02.pdf#page=28>).

### L2-G. Соглашения имён

**Положение лекции:** компонент может поддерживать несколько интерфейсов;
соглашение имён с префиксом продукта и обозначением версии помогает избежать
конфликтов. Пример — IEcoString1.
Источник: [L2, слайд 42](<../../../../Materials/Presentations/Проектирование - Лекция 02.pdf#page=42>).

### L3-A. Базовый интерфейс обязателен

**Положение лекции:** каждый интерфейс ACOM наследует IEcoUnknown и содержит
`QueryInterface`, `AddRef`, `Release`. Интерфейс без этих методов не соответствует ACOM.
Первый параметр C-метода — `me`.
Источник: [L3, слайды 2–6](<../../../../Materials/Presentations/Проектирование - Лекция 03.pdf#page=2>).

### L3-B. Назначение QueryInterface

**Положение лекции:** QueryInterface получает IID и адрес выходного указателя.
При поддержке интерфейса возвращает указатель на него, иначе код ошибки.
В реализации на слайде указатель обнуляется при неподдерживаемом IID;
перед успешным возвратом вызывается AddRef.
Источник: [L3, слайды 6–7](<../../../../Materials/Presentations/Проектирование - Лекция 03.pdf#page=6>).

### L3-C. Пять правил QueryInterface

Источник: [L3, слайды 8–18](<../../../../Materials/Presentations/Проектирование - Лекция 03.pdf#page=8>).

| Правило | Что означает для реализации и теста |
|---|---|
| Единая идентичность объекта. | QueryInterface для IEcoUnknown через любой интерфейс одного экземпляра возвращает одно и то же значение указателя. Не требовать равенства адресов всех остальных интерфейсов. |
| Стабильность поддержки. | Для живого экземпляра успешный запрос интерфейса остаётся успешным, неуспешный — неуспешным. Правило не сравнивает разные экземпляры. |
| Рефлексивность. | Через уже полученный интерфейс можно снова запросить этот же интерфейс. |
| Симметрия. | Если через IX доступен IY, через IY доступен IX. |
| Транзитивность. | Если через IX доступен IY, а через IY — IZ, через IX также доступен IZ. |

### L3-D. Счётчик ссылок и удаление объекта

**Положение лекции:** AddRef увеличивает число ссылок, Release уменьшает;
при нуле экземпляр освобождает себя. Показан общий счётчик объекта и вариант
отдельных счётчиков интерфейсов.
Источник: [L3, слайды 19–24](<../../../../Materials/Presentations/Проектирование - Лекция 03.pdf#page=19>).

### L3-E. Владеющая ссылка и заимствованный указатель

**Положение лекции:** вложенная жизнь локальной копии позволяет обойтись без
дополнительной пары AddRef/Release; если жизнь копии перекрывает жизнь исходной
ссылки, обе ссылки нужно учитывать.
Источник: [L3, слайды 25–28](<../../../../Materials/Presentations/Проектирование - Лекция 03.pdf#page=25>).

### L3-F. Правила параметров и хранения указателей

Источник: [L3, слайды 29–39](<../../../../Materials/Presentations/Проектирование - Лекция 03.pdf#page=29>).

| Ситуация | Правило и применение |
|---|---|
| QueryInterface, QueryComponent или другой метод возвращает интерфейс. | Возвращается уже добавленная ссылка; клиент не делает ещё один AddRef только из-за получения результата. По окончании — Release. |
| Выходной параметр `out` содержит интерфейс. | Перед возвратом добавляется ссылка для вызывающей стороны. При передаче уже имеющейся владеющей ссылки обеспечить тот же контракт, не удваивая счётчик. |
| Входной параметр `in` используется только во время вызова. | Обычно заимствован; время вызова вложено в жизнь ссылки вызывающей стороны, отдельная пара AddRef/Release не нужна. |
| Параметр `in-out` заменяет владеющий интерфейс. | Старую ссылку нужно отпустить, новой обеспечить владение. При совпадении объектов или других зависимостях порядок действий должен сохранять их жизнь. |
| Локальная копия `in` не покидает вызов. | Может быть заимствованной; действует правило вложенных времён жизни. |
| Интерфейс сохраняется в поле объекта или глобально. | Требуется собственная ссылка и её Release при замене/удалении; срок хранения уже не ограничен исходным вызовом. |

Эти правила относятся к **указателям на интерфейсы**. Число, выходной результат
интеграла или сырой буфер не получают AddRef автоматически. Для callback-функции
и её контекста необходимо отдельно описать срок жизни и хранение в DESIGN.md.

### L3-G. Защита времени жизни во время вызова

**Положение лекции:** при сомнении рекомендуется защитная пара AddRef/Release;
на слайде 41 показано удержание объекта на время выполнения функции.
Источник: [L3, слайды 40–41](<../../../../Materials/Presentations/Проектирование - Лекция 03.pdf#page=40>).
